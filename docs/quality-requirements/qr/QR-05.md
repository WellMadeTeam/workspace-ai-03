# QR-05: Diagnose A Failed Request From The Operating Signals

An operator can identify a failed request in the core task from the staging signals and see its effect on the request-duration SLI.

- **Status:** Active
- **Characteristic:** Maintainability
- **Sub-characteristic:** Analysability
- **Business importance:** High
- **Technical risk:** Medium

## Scenario

### Source

The system operator responsible for diagnosing the deployed product.

### Stimulus

An HTTP request in the core task fails on the staging deployment.

### Environment

The staging deployment sends its signals to the staging OpenObserve organization, and the production organization receives no test traffic.

### Artifact

The backend's structured request log and the staging dashboard for `SLI-01`.

### Response

The operator finds the failed request's log point by its `request_id` and sees the route, whether the outcome is `client_error` or `server_error`, and its duration; the dashboard shows the corresponding request-duration P95 as a number.

### Response Measure

Within five seconds of the failed response, a query of the staging organization returns exactly one log point for that request with its `request_id`, route, `outcome=client_error` or `outcome=server_error`, and `duration_ms`.
Within one minute, the staging `SLI-01` query returns the matching error series, keeping `client_error` and `server_error` separate, with a numeric P95.

## QRT-01

The operator sends the core-task traffic and one controlled failing request to staging, finds its log point in OpenObserve, and reads the staging `SLI-01` P95.

- **Status:** Active
- **Level:** deployed
- **Runs at:** The staging deployment at `$STAGING_URL`, its OpenObserve staging organization at `$OPENOBSERVE_URL`, and `SLI-01`, from a machine on the university network: `python scripts/check_sli.py "$STAGING_URL"`.

### Procedure

1. Deploy the release candidate to staging and confirm that the staging OpenObserve organization and dashboard are reachable from a machine on the university network.
2. On that machine, from a checkout of the same commit, install the script's dependencies with `python -m pip install -r app/backend/requirements.txt`.
3. Set `STAGING_URL`, `OPENOBSERVE_URL`, `OPENOBSERVE_USER`, and `OPENOBSERVE_PASSWORD` from the team's password manager.
   Set `OPENOBSERVE_URL` to the OpenObserve API base URL, including `/api` (for example, `https://op.dminc.dev/api`).
   Then run `python scripts/check_sli.py "$STAGING_URL"`.
   The script creates a board and AI block, sends a fixed diagnostic query, sends a controlled failing request with a unique `X-Request-ID`, and queries only the staging OpenObserve organization for that ID.
   Set `OPENOBSERVE_LOG_STREAM` if the request log is stored in a stream other than `default`.
4. Check that the script prints exactly one structured log point with the request ID, route, its actual error outcome, and duration, and exits successfully.
5. Within one minute of the failing request, open the staging `SLI-01` dashboard and check that its five-minute P95 query shows a numeric series for that outcome; `client_error` and `server_error` remain separate.
6. Check that the production dashboard still has the same `SLI-01` query and contains no traffic from this run.

**Pass when:** the script finds exactly one matching log point with a `client_error` or `server_error` outcome within five seconds of the failed response, the staging dashboard shows a numeric P95 for that outcome within one minute, and the production dashboard receives no test traffic.
