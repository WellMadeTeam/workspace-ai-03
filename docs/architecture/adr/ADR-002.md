# ADR-002: Push Board Changes To Members Over A WebSocket

- **Status:** Accepted
- **Created:** 2026-10-25
- **Updated:** 2026-10-25
- **Containers:** `frontend`, `gateway`, `backend`
- **Addresses:** [`FR-003`](../../functional-requirements/fr/FR-003.md), [`FR-004`](../../functional-requirements/fr/FR-004.md), [`QR-01`](../../quality-requirements/qr/QR-01.md)
- **Decision:** [`DEC-017`](../../decisions.md#dec-017)

## Context

Every member must see another member's change within two seconds, with none lost, per [`QR-01`](../../quality-requirements/qr/QR-01.md), and the 11th member must be turned away while the 10 keep working, per [`FR-004`](../../functional-requirements/fr/FR-004.md) and the customer's [`DEC-017`](../../decisions.md#dec-017).
The first slice polled the backend for the whole board every second, so the backend never knew who had the board open and could not count members, and each member sent a request every second even when nothing changed.

## Considered Options

- **Poll the backend every second.**
  It is what the first slice does and needs no open connection, but the backend cannot tell how many members are on a board, so the member limit cannot be enforced, and a change waits up to a full poll interval.
- **Server-sent events for changes, and plain requests for edits.**
  The backend can push changes, but each member still needs a second channel to send edits, and a member is only counted while the stream stays open.
- **One WebSocket per member and board.**
  The backend holds one open socket per member, so it counts the members, refuses the 11th at the handshake, and sends each change to the others as it happens.

## Decision Outcome

Chosen option: one WebSocket per member and board.
The `backend` keeps, per board, the members that are connected, turns away a socket that would be the 11th, and sends each change to the other members; the `frontend` reconnects when the socket drops, and the `gateway` passes the WebSocket upgrade through.

## Consequences

- **Time Behaviour:** a change reaches the other members as soon as the backend has it, instead of at the next poll, which [`QR-01`](../../quality-requirements/qr/QR-01.md) measures.
- **Cost:** the members of each board live in the backend process's memory, so the backend must run as one process, which [`CON-03`](../../product-vision.md#con-03) allows.
- **Cost:** the frontend must handle a dropped socket and reconnect, and the gateway must be configured for WebSocket upgrades.
